## The 116 failures, by cause (from /tmp/status_final.txt grouping)

## Working rules (important)

- You are NOT allowed to call WebFetch on hospital or ATS domains from this session: each one triggers an approval prompt on the owner's phone. WebSearch is fine (no prompt) for vendor API documentation, and WebFetch is fine ONLY on URLs that a WebSearch returned (documentation pages, vendor blogs). All probing of real boards happens on GitHub Actions: `probe.yml` (scraper/tools/probe.py captures HTML, XHR JSON bodies and network logs to ci-logs) and `live_test.yml` with `-f only=slug1,slug2,...` against `data/hospitals.json`. Read results with `git fetch origin ci-logs` and `git show origin/ci-logs:<path>`.
- Foreground sleep is blocked; poll with `timeout 20 bash -c 'while :; do :; done'`.
- You are the only process using git. Stage only your paths (scraper/, tests/, .github/workflows/, scripts/, data/hospitals.json, data/regions/*.json). Commit after every working increment with messages ending in the two attribution lines used throughout the repo history. `git pull --rebase origin main` before each push.
- Keep unit tests green (`python3 -m pytest -q tests`). Add tests for every new adapter against a hand-written fixture of the real response shape you captured.
- Ledger edits go through scripts/patch_hospitals.py (patches by slug in both data/hospitals.json and the region file).
- Dependencies: add `curl_cffi` (and anything else) to scraper/requirements.txt; the workflows install from it.
- The scrape has a 90 minute budget; keep new adapters efficient (API first, browser only when needed).

Then one full `scrape.yml` run (`commit=true`, `notify=false`) and a report: boards ok before/after, new adapters, which boards remain unreadable and why, and the exact next step for each of those (for example "needs ScraperAPI key" or "the hospital has no online job board; jobs are on Indeed only").
